# Windows の Google Chat 予約通知タスク運用

この手順はWindows環境専用です。Azure Linuxの本番環境には不要です。本番は[Azure Linux向け定期実行手順](AZURE_SCHEDULED_GOOGLE_CHAT.md)を参照してください。

## 対象と安全境界

- 実行用: [scripts/windows/run_scheduled_chat_notifications.ps1](scripts/windows/run_scheduled_chat_notifications.ps1)
- 登録用: [scripts/windows/register_scheduled_chat_task.ps1](scripts/windows/register_scheduled_chat_task.ps1)
- Windows PowerShell 5.1 / Windows タスク スケジューラ用。既存の再起動・Django 起動タスクとは独立しています。
- 両スクリプトとも **`-Send` なしでは dry-run**。登録スクリプトの `-Send` はタスクの実行引数へ `-Send` を保存します。手動実行時も送信には実行スクリプトの `-Send` が必要です。
- Django 側の送信許可は **`GOOGLE_CHAT_SCHEDULED_SEND_ENABLED=True` と管理コマンドの `--send` の二重 opt-in**。スクリプトはこの環境変数や `DEBUG`、送信先を設定・変更しません。登録だけでは送信機能を有効化しません。
- `-Environment` は必須で `development` / `production` のみ。管理コマンドへ `--environment` として渡し、`DEBUG=True` → development、それ以外 → production との一致を管理コマンド自身が検証します。環境の切替スイッチではありません。不一致はエラー終了します。

## 導入前の確認（送信せずに実施）

1. アプリ側のマイグレーション0081・0082が適用されていることを確認します。[config/settings.py](config/settings.py) は `GOOGLE_CHAT_SCHEDULED_SEND_ENABLED` を環境変数から読み込み、未設定時は False です。ラッパー側でこの保護を回避しないでください。
2. UI の入口は管理者向け「アナライズ」→「設定」→「Chat通知予約・配信履歴」です。専用画面のパスは `/summary/chat-schedule/`。月選択、投稿期限、期限通知日時、レポート通知日時、有効・無効を設定し、変更履歴と配信状況を確認できます。保存操作自体では送信しません。手動の既存 Chat 通知ボタンは予約設定の代替ではありません。
3. 同一の実行 Windows アカウントで、同じ配備先・設定・DB・メディアを使用することを確認します。実行 Python は配備先直下の [.venv/Scripts/python.exe](.venv/Scripts/python.exe) に固定し、作業ディレクトリは `-ProjectRoot`（既定はスクリプトから 2 階層上）に固定します。venv の activate や PATH の Python に依存しません。
4. 設定は [config/settings.py](config/settings.py) の `load_dotenv()` と子プロセスが継承する環境を使用します。タスクは登録した PowerShell セッションの一時的な `$env:` 値を保存しません。Web サーバープロセス専用の設定も引き継ぎません。実行アカウントから読める保護された配備設定を用意し、既存の継承環境による上書きにも注意します。ユーザー/システム環境変数の変更後はログオンセッションや関連サービスの再起動が必要な場合があります。
5. 開発では `GOOGLE_CHAT_DEV_WEBHOOK_URL` を専用スペースに設定します。`DEBUG=True` では本番 GAS への転送と本番 Webhook への補完は無効です。本番では `GOOGLE_CHAT_WEBHOOK_URL` と `GOOGLE_CHAT_GAS_WEB_APP_URL` の実効値を保護された管理経路で確認し、既定の接続先を無条件に信用しないでください。
6. **GAS リレーを使う場合は** [scripts/google_chat_notification_relay.gs](scripts/google_chat_notification_relay.gs) の `scheduled_card` 対応版を Apps Script に反映し、ウェブアプリを新バージョンとしてデプロイして使用 URL を確認します。ソースを保存しただけでは既存デプロイは更新されません。実行アカウントからの到達性・アクセス設定、対象スペース、応答 `ok` / `status` を確認します。直接 Webhook を使う場合は GAS の実効設定を空にするなど、主実装側の設定方式に従い経路を明確にします。
7. DB 読書き、必要なメディア、ログディレクトリへの権限を実行アカウントに付与します。URL、トークン、パスワードをタスク引数・スクリプト・公開ドキュメントに書かないでください。スクリプトと配備先は信頼できる管理者だけが変更できる ACL にします。

## 安全な有効化手順

以下は運用担当者が後で行う手順です。この実装・検証では実タスク登録も HTTP 送信も行いません。

1. まず送信フラグは無効のまま、対象環境の予約を UI で確認します。有効化する月、期限通知・投稿状況通知の日時、JST、配信台帳と送信先を確認します。
2. 登録スクリプトを `-Environment development -WhatIf` または `-Environment production -WhatIf` で実行して登録内容を確認します。`-WhatIf` はファイル存在確認だけを行い、Django の実行・環境一致検証・タスク登録はしません。
3. 同じ実行アカウントで、実行スクリプトを `-Environment development`（本番確認なら `production`）だけで実行します。これは明示的 `--dry-run` です。終了コード 0 と安全ログを確認します。**0 は本文・送信先・送信許可が妥当という証明ではなく、今回のコマンド実行成功だけを示します。対象予約がない場合も 0 です。**
4. 登録スクリプトを対象環境で **`-Send` なし**で実行すれば、既定 5 分ごとの dry-run タスクになります。最初の実行予定は登録 1 分後です。実行アカウントのログオン状態で、タスク スケジューラの「前回の実行結果」とログを確認します。
5. 本番移行前に、開発専用スペース・管理された予約で経路を検証します。主実装側の settings 読込み配備を確認したうえで、実行アカウントの設定に `GOOGLE_CHAT_SCHEDULED_SEND_ENABLED=True` を明示的に設定します。この値をスクリプトから自動設定しないでください。
6. 手動の実行スクリプトで `-Send` を指定したときだけ `--send` が渡ります。**到来済みの有効予約すべてが最大件数まで対象**になるため、検証対象以外を事前に無効化します。`-MaxCount 1` でもどの月・種別が最初かは管理コマンドの選択順に依存します。
7. 定期実送信へ変更する際は既存 dry-run タスクを停止・無効化し、実行中プロセスの終了を確認してから削除します。その後、登録スクリプトに対象環境と **`-Send` を明示**して再登録します。同名タスクは暗黙に上書きしません。別名で送信タスクを増やさないでください。登録により即時実行はしませんが、1 分後以降は送信し得ます。
8. 緊急停止はタスクを無効化し、実行中なら停止します。フラグも無効化し、次回プロセスへ反映します。既に受理された HTTP は取り消せません。停止後は必ず Chat 実物と台帳を照合します。

### パラメーターとタスク設定

| 項目 | 既定 / 動作 |
| --- | --- |
| `-Environment` | 必須。development / production |
| `-ProjectRoot` | スクリプトから 2 階層上。別配備先を指定する場合も同じ構成の venv が必要 |
| `-Send` | 指定時のみ送信モード。登録・実行の両方で既定 off |
| `-MaxCount` | 20、範囲 1〜100。管理コマンドの `--max-count` |
| `-TimeoutSeconds` | 240 秒、範囲 10〜3600 |
| `-IntervalMinutes` | 登録用のみ。5 分、範囲 1〜1440 |
| `-TaskName` | 登録用のみ。KB-Scheduled-Google-Chat。同名があれば失敗 |
| 多重実行 | タスク側 `IgnoreNew`、実行側は配備先単位の排他ファイルロック |
| 実行上限 | 子プロセスは指定秒数後にツリー停止。タスク自体も指定秒数 + 30 秒で終了制限 |
| 再起動 | `RestartCount=0`。失敗時の自動再起動なし |

定期ポーリングは、終了済みタスクの失敗した送信を再試行する設定ではありません。実行中に次の時刻になっても並列起動せず、キューへ蓄積しません。PC の停止・スリープ中は実行できず、復帰時の即時補完や起動保証は設定していません。次の通常ポーリングで対象が判定されます。48 時間超過は管理コマンドが送信対象外にします。

## 実行アカウントと資格情報

登録時の現在の Windows ユーザーを `Interactive` / `Limited` で使用します。**そのユーザーがログオンしているときだけ実行**され、ログオフ後やログオン前の無人実行には向きません。管理者昇格・SYSTEM への切替・パスワード入力や保存は行いません。登録権限がなければ失敗終了します。

常時無人運転が必要なら、組織の管理者が専用サービスアカウント / gMSA 等の適切な principal、バッチログオン権、ネットワークアクセス、ユーザープロファイルを設計し、別途管理された方法で構成してください。S4U はネットワーク資格情報や暗号化ファイルへの制約があるため安易に切り替えないでください。Web と同じ環境・DB・接続先を解決できることが重要で、単に管理者で動かせばよいわけではありません。実行ポリシーは組織の署名ポリシーに従い、この登録では Bypass を付けません。

## ログ・終了コード・結果不明への対応

ログは配備先の [logs/scheduled_chat](logs/scheduled_chat) に UTC 日別で作成します。記録するのは UTC 時刻、環境、モード、固定イベント名、終了コード、経過時間のみです。標準出力・標準エラーは同時に null ストリームへ破棄し、一時ファイルにも保存しません。**dry-run でも本文を表示する管理コマンドの出力を全文ログに残すことはありません。** URL、カード、記事・氏名、例外全文も転記しません。ログの保管期限と ACL は運用側で管理してください。ログローテーションによる自動削除は行いません。

| 終了コード | 意味 |
| --- | --- |
| 0 | コマンド正常終了、または登録成功 / WhatIf |
| 1 | 実行準備・ラッパー・登録のエラー、または Django コマンドのエラー |
| 75 | 排他ロック取得不可（他実行中またはファイルアクセス問題） |
| 124 | 実行時間超過、子プロセス停止 |
| 125 | 子プロセス停止を確認できなかった |
| その他 | 子プロセスの終了コードをそのまま返却。PowerShell 自身の引数エラーも非 0 |

`runner.lock` は終了後も残します。存在自体は実行中の意味ではなく、OS の排他ハンドルで判定します。稼働中に削除しないでください。同じ DB に複数配備先・別ホストから接続するケースはこのファイルロックでは保護できないため、単一の運用タスクに統一し、バックエンドの台帳保護も維持してください。

タイムアウト・HTTP エラー・中断は、Chat 側で受理された後に発生する場合があります。**`unknown` は自動再送しません。** 失敗 `failed`、送信中 `sending`、結果不明 `unknown` の台帳を管理画面で確認し、送信先と照合して人が判断してください。古い `sending` は管理コマンドの実送信モードで claim から 30 分後に `unknown` になります。`pending` へのリセット、台帳削除、予約の複製による再送を自動化しないでください。Windows の再試行設定も追加しないでください。

終了コードだけでは送信件数や失敗理由は分かりません。詳細は台帳を安全な管理画面で確認します。環境不一致・フラグ未許可・DB 設定等の診断で管理コマンドを直接使う必要がある場合は、送信フラグなしの dry-run に限定し、本文が表示されるため共有ログ・Transcript・収集基盤への出力を避けてください。
