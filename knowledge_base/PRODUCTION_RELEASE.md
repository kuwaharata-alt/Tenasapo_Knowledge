# 本番適用の準備と確認

## 今回の対象

画面・入力フォーム・マニュアル・投稿目標・投稿レポート／PDF・Chat予約通知の変更と、単発スクリプトのOLD退避をまとめて適用します。開発DB、添付ファイル、秘密設定、Windowsタスクの登録状態は移行しません。

## 現在の判定：CI再検証・本番データ保全の確認待ち

2026-11-13の初回全体テストは574件中、失敗52件・エラー1件でした。旧テストの入力・プロフィール・応答・一覧表示を現行の契約に合わせて修正しました。テストの削除・スキップ追加・実行時の認可や入力制約の緩和はしていません。開発環境がReportLab 5.0.0なのにCIは4.0.9だったため、依存関係も5.0.0へ統一しました。修正後のローカル全574テストは成功しています（テストプロセス内だけ高速なパスワードハッシャーを利用し、本番・ソース設定は変更していません）。GitHubの固定依存関係で再検証し、本番データ保全も別途確認します。

局所的な再現とHEAD版との比較で、以下を確認しました。全失敗の原因が確定したわけではありません。

- 認可拒否の302と旧テストの403期待、登録時の必須入力不足、プロフィール未設定時のLP誘導は、HEAD版にも同じ実装／入力検証があります。これらを理由に認可や入力制約を緩めません。
- 回答画像テストは画像を添付モデルへ保存していますが、現行・HEAD版の描画は別の画像モデルを参照します。既存の期待不整合／不具合として別途判断が必要です。
- デモ向け一覧は「タイトル・質問を表示し、回答／本文を制限する」変更があり、旧テストの「記事全体を非表示」と衝突しています。新しいデモ閲覧仕様のテストは成功していますが、旧テストを含めた仕様の統一と再検証が必要です。

## GitHubでの検証と承認

1. 作業ブランチをpushすると、リポジトリルートの本番ワークフローがチェック・全アプリテスト・静的ファイル生成・配布物の作成を実施します。作業ブランチとPRではAzureへ配備しません。
2. ActionsでPython 3.12と[requirements.txt](requirements.txt)の固定バージョンを使った検証結果を確認します。ローカル環境の成功だけでは、この検証の代わりになりません。ブラウザ未導入のテストはスキップされるため、主要画面は別途実操作で確認します。
3. 配布物はOLD、秘密設定、仮想環境、SQLite、バックアップ、メディア、保存メール、ログ、キャッシュ、ローカルデータダンプを除外します。元リポジトリに既に追跡されたデータがあっても配布しません。ただし、Git履歴のデータ削除や秘密情報監査は別の作業です。
4. mainへのマージ／pushも検証と配布物作成のみです。**Azureへ配備するには、mainを選んで手動実行し、`production_ready`を有効にする必要があります。DB・メディア保全と移行計画の承認前に有効にしないでください。** Publish Profileは既存のGitHub Secretを使い、リポジトリには保存しません。

## 本番で事前に必要な確認

- 対象は既存ワークフローのApp Service `nexus-app` / Productionです。Azure実リソース、ホスト名、Python 3.12以上のランタイム、Oryxビルド設定、起動コマンドを運用担当者が確認します。CIでの依存関係インストールはAzure側のインストールを保証しません。
- 本番は`DEBUG=False`、PostgreSQL接続と既存の秘密設定を維持します。開発用Webhookや`GOOGLE_CHAT_SCHEDULED_SEND_ENABLED=True`をコピーしません。
- App Serviceのメディア保存先と永続化方式を確認し、DBとは別に保全します。今回の配布物にはローカルメディアを含めません。
- PostgreSQLの復元ポイント／バックアップを確保し、復元先・復元手順と直前の適用済みマイグレーションを確認します。ローカルSQLiteバックアップは本番の復元に使えません。
- メンテナンス時間、書込み停止、通知ジョブ停止、旧コードへ戻す手順を準備します。可能なら本番相当のPostgreSQL・ステージングで先に移行を検証します。

## DB移行は別途必須

今回の新規マイグレーションは0073〜0082です。実際に未適用の範囲は、本番の状態で決まります。ワークフローはソース配備を行いますが、**本番のDB移行は自動実行しません**。

新コードの公開前にメンテナンス状態にし、配備後のアプリ環境・依存関係・本番DB接続を使って、適用計画を確認したうえでDjangoの`migrate --noinput`を一度実施します。移行完了を確認するまで通常アクセスと通知ジョブを再開しないでください。Azureへの接続方法と実行用Pythonは実環境に合わせて決定します。

- 0079：既存の目標履歴を月別へ展開します。初期目標が空の場合は自動で数値を投入しません。
- 0082：既存の通知予約を無効・環境未割当にします。既存予約がある場合は確認・再設定が必要です。
- データ変換の逆操作では元データ状態を復元できません。問題発生時にマイグレーションを戻すだけで復旧できるとは限りません。
- ローカルデータの再投入、SQLiteからの再移行、既存ユーザーや記事の上書きは不要です。

## 適用後の確認

ログイン、記事・Tips一覧、投稿・承認、添付、マニュアル、アナライズ、月別集計、PDF、通知予約画面を確認します。DB接続・静的ファイル・サーバーログも確認し、問題がないことを確認して通常アクセスを再開します。

予約通知の自動送信は別途[Azure Linux向け手順](AZURE_SCHEDULED_GOOGLE_CHAT.md)で導入します。最初は送信許可を無効にしたdry-runとし、運用承認後にのみ実送信へ切り替えます。ソース配備だけで本番の自動送信を開始しません。
